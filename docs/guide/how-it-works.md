# How it works

- **Companion verification.** The `flow-clone` and `verify-factory-flow` skills drive dashboard DOM controls on an isolated loopback port. Readiness expects `/` to redirect (302), `/dashboard` to load (200), and the floor list to appear. Shell proof exercises hire, a terminal command with a file side effect, and confirmed removal; the MCP probe requires 401 for Shell credentials. Doctor checks only the isolated run, and cleanup preserves evidence outside scratch state. Mac-window checks require a matching signed app.

- **Companion entry points.** The Vite build ships only `dashboard.html`. `/` and `/index.html` redirect to `/dashboard`; `/open/worker|question|floor|card/<id>` redirects to its companion target, without credentials. Worker, floor and Whiteboard targets survive initial connection and floor switching. Remote browser access can be disabled without disconnecting direct loopback browsers or the Mac window; paired Android phones remain unaffected.
- **Gemini connection.** `src/server/gemini-connection.ts` retains key connection, explicit verification, disconnect and the wake-filter preference. Probes are cancelled on disconnect, key changes and airgapped mode. There are no periodic mood requests.

- **Inter-agent noise gate.** With Gemini Decisions connected, **Inter-agent noise gate & smart wakeup filter** (`wakeFilterOn` in `gemini.json`, on by default) sends each non-urgent `team_report`, subagent `done` event, `lead_notify` update, interrupting `team_note` and visit tell through one scrubbed `gemini-decision-1` call (`src/server/wake-filter.ts`) that weighs the lead's task, plan and terminal, the team board, the sender's recent chatter and the message. It wakes the lead now, holds a completion until the batch settles (10-minute ceiling), records a routine update without waking anyone, or, under deterministic guardrails and two high-confidence chatter locks, coaches the sender instead; notes reach only relevant siblings. Questions, blockers and urgent messages always wake, everything stays readable through `team_status` and `office_inbox`, and every failure delivers as before. See [Office MCP](../office-mcp.md#inter-agent-noise-gate).

- **Grok Bot connectivity tests.** Settings **Send test** uses `RemoteOffice.testWebhook` to send a test-only message and action hint asking the bot to confirm receipt to the owner and report all non-secret payload fields and any received request id (or its absence). Authorization headers, webhook keys, tokens and other secrets must never appear in that reply. The test does not create an inbox acknowledgment or worker task; real worker event instructions are unchanged. See [Mission Control](../mission-control.md#external-bots).

- **Active-manager guidance and evals.** Default Orchestrator, worker and MCP instructions teach leads to assign single-writer scopes, inspect in-flight work, relay sibling contracts, answer in-scope technical questions, escalate permission prompts and sequence reviewed integrations with combined checks. `team_review` approval is a lead workflow gate, not a server-enforced merge lock. The isolated `tools/orchestration-eval/` harness measures default role contexts and synthetic coordination scenarios through real MCP schemas with simulated worker/Git backends; its offline grader tests run in CI, including on harness-only changes.

- **Sibling coordination and mid-turn steering.** Subagents use `team_board` for their same-floor siblings' task titles, status, branch, declared edit areas, latest note and the existing structured result's status/summary (or report prose when absent). This is an in-memory read, without terminal or Git inspection or consuming lead news. `team_note` publishes a finding, optionally replacing edit areas, and delivers a fenced worker note only through current hook notices to working siblings that have not reported this turn. Other workers read the saved board without new queued input or wakeups. Leads see edit areas and notes in status and waits. Latest notes and areas persist in the floor's `team.json`. New hires automatically receive a snapshot under 2,600 characters outside the task fence; their saved prompt stays the literal task. Leads use `team_message` for one worker, a `workers` subset or `all: true`; building-agent broadcasts span their teams across floors unless a floor is named. The default queued mode delivers busy-worker guidance on the next tool hook, or Ctrl+Enter behind the turn on older sessions, without interrupting. Delivery receipts distinguish next-step, queued-turn, sent, resumed and individual errors. Broadcasts deduplicate resolved ids, include names and building-team floors, and return errors for empty teams or entirely failed deliveries.

- **Worktree handoff and integration.** Office MCP `team_hire` accepts `from` or structured `task.baseBranch` as a branch, `worker:<name or id>`, or any registered worktree's absolute path, including kept/dismissed and retained integration worktrees; canonical aliases and detached HEADs are supported. Worker/path handoffs pin committed HEAD into a fresh worktree, return provenance and leave the original worker and dirty files untouched. `team_merge` merges or cherry-picks a reviewed worker into the lead's branch or an explicit existing local target (required for Mission Control). `team-integrate.ts` uses an existing target worktree, or creates one under `.factory-flow/worktrees/integration-*` for an unchecked-out target without switching the shared checkout. Self-targets, occupied targets, dirty worktrees and existing Git operations return structured blocked results. Non-conflict failures abort or quit the attempted operation and remove temporary worktrees; only actual conflicts retain a temporary worktree. Conflicts retain Git's state and return a blocked result with paths, ours/theirs hunks, index stages, target HEAD and exact continue/abort instructions; a temporary conflicted worktree stays for resolution. Clean results include one-line landed summaries and artifact commit/file provenance. `team_pr` uses the floor's forge to open an authorized PR/MR from a worker branch whose local HEAD matches origin, without implicitly pushing. Its default base is the recorded starting branch then the floor branch. The PR is recorded on the worker card, persisted by `WorkerManager.recordPull` and refreshed on the board. Default cherry-picks exclude patch-equivalent changes already landed on target. The Orchestrator brief calls for review, integration and combined target checks before dismissal.

- **AskUser final review.** The shared server/web parser and Android's `Choices` recognize Droid 1.7.1's **Review your answers** only with its focused **Submit answers** row, answer summary and live Enter/ESC footer. A review menu carries those exact `review` lines, one explicit **Submit answers** option and no typed answer. Web and Android Asks/Thread workspaces show the summary and a pinned submit button; opening or selecting earlier answers never submits the review automatically. `Answers` rechecks the current menu before sending Enter, and menu equality and MCP question ids include the summary so another device's edits invalidate stale submissions. `question_answer` uses option `1`; `office_worker_answer` preserves the exact review snapshot. Legacy numbered menus and CLIs without a final review retain their behavior. The real 1.7.1 capture in Android test resources is shared with server tests.

- **Account-free Droid setup.** The welcome's Factory step offers **Use without an account (airgapped)**, also switchable in **Settings → Connections → Droid**. Office-wide `setup.json` stores `airgapped` alongside `onboarded`; absent means account mode. While enabled, setup checks skip auth and require an installed Droid and usable configured custom model. Worker/Office MCP catalogues exclude hosted models, and worker model gates refuse hosted defaults and unknown ids. Factory account/usage UI and API/cloud actions are unavailable, while saved credentials remain intact for switching back. Mode changes immediately broadcast the empty or restored Factory state even when the registry cache is unchanged; window watches remain current without polling while paused. This is no-account mode, not network isolation: public Droid can still contact Factory, Office still checks updates, and existing turns are not stopped. See [Setup and Subscriptions](../subscriptions.md#airgapped-no-account-mode).

- **Android worker card actions.** An ordinary tap opens the worker; long-press (on either the building-wide **Workers** tab or the floor-scoped **Office** tab) opens a Material modal bottom sheet with only **FORK** and **DISMISS**, dismissible with Back or outside interaction. Fork mirrors `worker-fork.ts` eligibility, explains disabled states, confirms an optional direction and sends `worker.fork`. Dismiss reuses the send-home confirmation and worktree risk checks, with **Keep both** selected by default and cloud-session deletion opt-in. Both use floor-scoped action receipts against the worker's own floor, recheck the current worker and connection before sending, block duplicate submits and report unconfirmed outcomes without replaying. Removing the worker or its floor closes the card flow. On worker cards, Working is the existing animated equalizer and Done a solid green indicator without text or a pill border; spoken statuses, unseen-completion semantics and the other status labels remain.

- **Companion pane actions.** Closing a pane removes it and shrinks the layout by one; closing the last pane leaves one empty pane. Surviving panes keep their terminals, history and drafts, hidden workers stay hidden, and Auto pauses until selected again. Closing never sends the worker home. In the native Mac companion, **⌘W** runs Close Pane and **⇧⌘W** opens the existing send-home confirmation for the focused worker. The final empty pane stays open; ⌘W dismisses an open context menu or dialog before touching panes. Electron consumes these chords before page input and menu accelerators, ignores held-key repeats, and delivers only to its own office's `/dashboard` (`companion-commands.ts`). The Window menu provides the same actions and a separate, unbound Close Window. Browser shortcuts are unchanged. Right-click a worker or shell sidebar entry (or use Shift+F10 / the context-menu key) for grouped Workspace, Worker and Copy actions, plus Send home. Actions use the clicked worker, not the focused pane; unavailable actions are disabled or omitted. Menus dismiss on outside interaction, Escape, Tab, sidebar scrolling, resizing, floor changes, disconnects and relevant worker changes, and recheck eligibility before running.

- **Team status news and floor watching.** Remote `team_status` keeps a per-caller sequence cursor in the floor's `team.json`, separate from `office_inbox`'s explicit acknowledgments. The first status call establishes a baseline without replaying old reports; subsequent calls return only newer events that have not already been acknowledged in `office_inbox`, including across reconnects and office restarts. Passing a single-floor `since` event id leaves unmentioned floors on their normal unread cursor rather than replaying from zero. Reading status does not acknowledge inbox messages. Every prose news item includes its UTC timestamp. `team_watch` lets leads and building agents follow or unfollow independent floor workers (`watched` and `pullStates` persisted in `team.json`) without setting `WorkerInfo.lead`, changing their system prompt or Stop hook, or hiding owner attention; watched workers appear in `team_status`, `team_wait` and `questions_list`, wake leads (including Grok Bot webhooks) on turn completion, terminal `AskUser` menus, stops, departures and pull-request open/merge/close transitions (`pr`), and cannot be dismissed via `team_dismiss`. Floor-wide `team_status` also lists independent `floorWorkers` on the floor so leads never miss owner-started sessions, `office_roster` reports each worker's working directory, live `.git/HEAD` branch and checkout safety warnings when live writers share a working tree or sit on `main`, and new hires/forks get names unique across live workers on all open floors. Slots the office picks itself (`auto` desks, `team_hire` subagents, forks; `WorkerManager.pickSeat`) avoid slots live workers hold on other floors while another is free, while a slot a caller names is refused only when it is taken on its own floor. An external worker's `office_whoami` counts subagents across all open floors. Its `office_look` worker snapshots keep at most the latest 48,000 characters and mark truncated output.

- **Mission Control and external MCP workers.** Building agents have no floor or slot (`deskId: ''`) and never appear in floor worker lists. `remote-workers.ts` keeps external bot identities, keys and explicitly acknowledged inbox messages in office-wide `remote-workers.json` (mode `0600`); legacy desk fields load without taking a slot. `orchestrator.ts` owns one slotless Droid session, launched on its first prompt in `.factory-flow/orchestrator/`, with settings in `orchestrator.json` and nested worker/PTY state in `orchestrator/.factory-flow/`. It authenticates through the existing loopback hook listener using its own terminal hook token; a floor worker's token cannot impersonate its reserved id. Its scoped PreToolUse approval covers the building agents' Office MCP tools by exact name; shell/native/other MCP permissions and the Task denial remain. Pre-start trust menus become owner-answerable Asks. Turning it off stops its session and reset starts a new conversation; its team stays its own through both and through an office restart, with reports refused while it is off and waiting for it between conversations. A prompt for a session that ended resumes it, pictures included. A prompt sent from a floor (the connection's active floor; none from Mission Control) ends with one plain line, `Factory Flow notice: The owner sent this from the <floor> floor (<checkout>).`, on the prompt that starts a conversation and whenever the floor differs from the last one named (`Orchestrator.prompt`). It is not a `<system-reminder>`: the Droid TUI escapes a reserved tag typed into a prompt (`&lt;system-reminder&gt;`), so the model would read literal text. A UserPromptSubmit hook's `additionalContext` was not used because a queued (Ctrl+Enter) prompt fires no such hook. The Thread, the office's labels and cloud threads hide a raw reminder or notification block, and in the owner's own messages that line and a closed escaped block (`hideOfficeText`; an assistant quoting a lone escaped tag is left alone), so the message stays what was typed, and New conversation or an office restart starts the naming over. Team reports, questions and finishes wake it through the ordinary resting-lead path. Readiness, model and Office MCP setting changes rebroadcast Mission Control without needing a new prompt. While it can't start, `orchestrator.blocked` carries the reason and `orchestrator.blockedPane` the Settings pane that fixes it (`connections` for Droid, `subagents` for the Office MCP, none for a model that can't run). A new model or effort restarts its session when its turn ends and resumes the same conversation; a session that ended before then starts on the new model with its next prompt, once. The owner's office handler that Office MCP tools and building agents act through (`createOwnerOffice`) lives in `src/server/server-runtime/owner.ts`. `missionControl` is building-wide state on every client and floor; its `orchestrator.team` lists the Orchestrator's subagents whether or not it has a session. MCP discovery includes a dormant configured Orchestrator without launching a PTY. The Orchestrator and bots use the building-wide surface: external bots list a fixed set of tools and the Orchestrator omits self-reported `office_status`. Building agents have no visits. Hires name an open floor via `floor` or `task.repo` (id, name or path; a shared name or two different floors is refused); structured bases are optional and read-only checkout work uses `worktree: false`. Building agents bypass Subagents permissions and per-lead caps, but obey capacity, model availability and the Subagents model allowlist (`model-policy.ts` holds the single source-of-truth rule for floor leads, the Orchestrator and external bots alike, checking explicit models and resolved defaults and naming the allowed ids on refusal; `Team.refuseSpawnModel` checks spawns in `ownerOffice.act`, including cloud spawns and omitted models, before the owner's handler runs, while leaving existing workers' saved models and the owner's own window hires untouched). `team_hire` takes `from` and a structured task's `baseBranch` for one setting: `main` and `origin/main` agree, the structured `baseBranch` is what the hire uses, and different bases are refused naming both. `office_roster` lists Mission Control separately. Control tools act only on floor workers; `office_look` and `office_worker_thread` may read the Orchestrator, but building agents cannot prompt, interrupt, answer or dismiss one another or themselves. Strict schemas, fixed allowlists, server-generated request ids and the ordinary owner handler enforce this. Dismissal preserves worktrees, branches and cloud sessions unless deletion was requested; uncertain outcomes never authorize replay. `RemoteMcp` keeps its separate loopback listener (4711 unless taken), serving `/office/mcp` and `/office/images` (`office-images.ts`), behind Tailscale Serve on a free HTTPS port (9443–9449 or 11443), never Funnel or another service's mapping. Requests require the owner's tailnet device identity (or a tagged device), no browser Origin, and a bot key in `Authorization: Bearer` (never in URLs or logs); the key alone identifies its bot, with optional matching worker-id header. Bots upload bounded (`<= 25 MiB`), magic-byte-validated raster images (`PNG`, `JPEG`, `GIF`, `WebP`) to `POST /office/images`, receive content-addressed 16-hex ids stored in office-wide `.factory-flow/images/` (LRU-pruned at 500 images / 512 MiB), attach those ids in `team_message`, `team_hire`, `office_worker_prompt` and `office_worker_spawn` (adopted into each recipient's drops folder), and fetch images produced by workers (`team_report`, `lead_notify`), placed on floor Whiteboards (`whiteboard_read`, including `png: true` rendered card tiles), or viewed in `office_worker_thread` via clean token-free `{ id, url }` metadata and `GET /office/images/<id>`. Bots have named keys with last-use timestamps, JSON-only responses and inbox acknowledgment. Individual external bots can be marked as **Grok Bots** (`grok-webhook.ts`, `remote-workers.ts`, `remote-office.ts`) with a per-bot HTTPS webhook URL and `Authorization: Bearer` secret stored in mode-`0600` `remote-workers.json` (the secret is stripped from client state and redacted from delivery errors). While any Grok Bot exists, `RemoteOffice` subscribes to open floors' `Team` events, coalesces hook bursts, immediately flushes all `team_report` reports, including progress and questions (suppressing duplicate post-report `done` events), marks successful final worker snapshots done/settled with `taskComplete`, sends outcome-first bounded summaries and structured results with full-report references instead of duplicate prose, omits redundant phase/state and inferred question summaries while retaining operational id aliases, uses change-artifact-aware action hints without merge prerequisites for no-artifact reports, scrubs overlapping raw/encoded credentials from prose and errors before clipping while preserving protocol values and opaque references, pushes inbox messages, exposes `Send test` on `/api/remote-mcp`, and unlocks mid-turn `lead_notify` for subagents whose lead is a Grok Bot while leaving non-Grok bots polling-only. `FACTORY_FLOW_REMOTE_MCP=off` keeps clones and CI off the tailnet without disabling the Orchestrator. Clone preparation preserves `orchestrator.json` but excludes its whole session folder. See [Mission Control](../mission-control.md), [external workers](remote-workers.md) and the [MCP reference](remote-mcp.md); transport tests keep the exact tool list current.

- **Office MCP.** `src/server/office-mcp/` mounts one `factory-flow` server at `/office/mcp` on the loopback hook listener. Every protocol request proves the caller with its bearer hook token and `x-factory-flow-worker-id`; shells and cloud workers are refused. Per-request predicates hide unavailable tools and refuse direct calls to them. `office_whoami` reads identity and permissions. `team_status`, `team_message`, `team_review`, `team_dismiss`, `team_hire`, `team_models`, `team_report`, `team_wait`, `team_report_get`, `questions_list` and `question_answer` manage teams; `team` remains a deprecated compatibility alias. Owner worker tools (`office_look`, `office_send_home`, `office_worker_prompt`, `office_worker_answer`, `office_worker_interrupt`, `office_worker_thread`) and visit tools (`visit_look`, `visit_message`) accept `worker` consistently alongside `workerId`/`name` aliases (and `office_worker_prompt` accepts `prompt` or `text`). `team_report` attaches a structured `WorkerResult` (`status`: `ok`, `blocked`, `failed` or `partial`, `summary`, optional `artifacts`, `remaining` and `conflicts`), inferred when omitted, and `team_review` records a `verdict` (`approve`, `request_changes` or `comment`) and notes on the subagent's latest result (including after the subagent has been dismissed; sending `request_changes` notes back to an active subagent by default), surfaced across `team_status`, `team_wait` and `team_report_get`. `team_status` (and `team` action `status`) is a non-blocking poll: it drains that lead's news (reports, questions, finished turns and departures) since its last request and returns a snapshot with idle duration, plan steps/progress, current/last tool span, hook silence age, queued terminal/notice counts, live `queuedMessages` and active `blockingTool` hints, subscription model retry/cooldown status, cached PR/CI/Release status (`worker-status.ts`), and `taskLabel` provenance, optionally with terminal lines, plus compact structured workers, typed events with ids and a cursor (`since`, `kinds`, `verbose: false`). `team_models` prepends a compact per-provider `Subscription quotas:` summary, triggers a 15-second-throttled DroidProxy `/models` recheck, and filters via `only` (`all`, `subscriptions`, `available`, `quotas`); `models_list` additionally includes switched-off and disallowed models. Hiring accepts top-level `title` + `brief` or a structured `task` with optional `repo`, `baseBranch`, `branch`, PR number and acceptance criteria (working on both Git and non-Git floors), returning the worktree path and branch immediately. `worker_diff`, `worker_log` (`tail: 0` for structured worker state without terminal text; `office_look` likewise supports `lines: 0`), and `worker_queue` provide bounded read-only work/activity inspection (`worker_diff` also inspects dismissed subagents whose worktree or branch still exists, persisted under `former` in `team.json`) and pending-message queue control (`list`, `clear`, `promote`, plus `urgent` interrupt-and-steer when a worker sits in a blocking command). `worker_model` switches a subagent's model with the words typed after `/model` (`Sol`, `droidproxy sol`), driving Droid's own picker in a running session or pinning the model for an asleep one's next launch. `team_message` and `office_worker_prompt` both default `queue` to `false` (steering during a running turn), queue behind the turn only on `queue: true`, and interrupt via Escape on `urgent: true`, while `team_status` and `office_roster` surface `queuedMessages` and active `blockingTool` hints. Diff inspection requires a Git floor; a plain folder never discovers an enclosing checkout. Reports retain optional pushed SHA and PR URL fields alongside prose. The new dismissal tool keeps worktrees and branches by default; optional pruning refuses busy, dirty, detached or non-owned worktrees, never forces Git removal, and only requests safe local branch deletion. Observed idle timestamps survive office restarts in `team.json`. Tool failures include `isError` and structured `code`/`hint`; HTTP 401/400 failures also carry these fields without changing status codes or the SDK's JSON-RPC error. The office wakes a resting lead; with "Wake the lead" off, and for external workers, `team_wait` long-polls for news instead, capping each single call hold at 90 seconds under MCP client request timeouts (`-32001`) and returning `matched: false` with a continuation `cursor`. `office_inbox` supports `ids` and webhook `deliveryId` scoping so overlapping webhook runs see already-acknowledged items (`acked: true`) and never acknowledge another run's items. `questions_list` and `question_answer` answer subagents' questions, terminal AskUser menus included, through the phone's answer queue; permission prompts stay with the person. Visit asks are non-blocking and answers arrive later as deliveries. Whiteboard mutation tools operate on the caller's floor, while `whiteboard_read` also accepts `floor` for building agents, returns requested PNGs as MCP image content, preserves per-card read-point semantics, and surfaces downloadable `{ id, url }` entries for card images, picture marks and rendered tiles. The **Office MCP** switch in Settings defaults on (`SubagentSettings.officeMcp`, saved in `subagents.json`). Startup merges one header-variable-based `factory-flow` entry into `~/.factory/mcp.json`, preserving unrelated servers and refusing malformed or foreign entries; turning it off removes that entry while it points at this office and immediately gates requests. Offices on one machine share the entry: the `x-factory-flow-url` header (`${FACTORY_FLOW_HOOK_URL}`) lets whichever office it points at relay another loopback office's workers to their own office, and an office takes the entry over at startup or within 30 seconds once its holder stops answering. A Droid session outside the office has no identity variables, makes no MCP request and keeps its ordinary tools. Hooks still use their process-local runtime overlay. The server is the official MCP SDK (`@modelcontextprotocol/server`), stateless, building one server per request for its caller, and it refuses a request whose `Host` is not a loopback name. See [the Office MCP plan](../office-mcp.md) for details.

- **Companion worker teams.** The sidebar keeps each main worker and its hired subworkers together in creation order, using `WorkerInfo.lead`, never team badges or fork links. Connected child rows, a Lead label and main/subworker totals make the relationship explicit. Teams collapse independently; their working counts remain visible when collapsed. Shared helpers in `src/shared/team.ts` keep grouping and counts consistent with the terminal and companion: starting workers count as working, and every terminal input request needs the owner's attention, including a subagent's question. Subagent completions stay with their lead. Questions retain their attention rings, needs-you badges and companion answer prompt, including in the team navigator and Team activity. A compact team navigator above both Thread and TTY switches the current pane between the lead and its subworkers. Keyboard worker navigation reveals hidden children; sidebar arrows follow visible rows. New arrivals fade and slide into their team once, without replaying on status ticks, floor changes or reconnects, and respect reduced motion. Missing or invalid lead links leave workers visible rather than hiding them.

- **OpenAI-compatible worker-label endpoints.** Worker labels can use **OpenAI-compatible endpoint** instead of the default Droid implementation below. Enter a server root (`http://localhost:11434`), `/v1` base URL (`https://api.openai.com/v1`), or full `/chat/completions` URL, a model slug, an optional Bearer API key, and an optional `reasoning_effort` (omitted by default so standard chat models never fail). Remote hosts require `https://`, while `http://` is accepted on localhost, private LAN and Tailscale hosts; redirects and cloud-metadata/link-local addresses are refused. API keys are stored only in mode-`0600` `.factory-flow/worker-labels.json`, never returned to clients, and never reused across different URL origins. **Test endpoint** verifies connectivity and JSON label parsing with a sample conversation before or after saving. Calls run directly over HTTP (no Droid install or Office Factory key required) with the same bounded visible-text input, global queue, backoff, stale-result protection, 45-second timeout and 256 KiB response limit, stripping inline `<think>` blocks and never echoing raw provider error bodies. Legacy `custom` script configurations load disabled on upgrade so they do not unexpectedly switch to Factory credits. See [OpenAI-compatible label endpoints](worker-label-endpoints.md).

- **Worker labels.** **Settings → Workers → Worker labels** controls the stable task subject and one-line current-work summary for every Office-managed local Droid, including subagents. The default is `glm-5.3-flash`, low reasoning, every 60 seconds, enabled with the Office's Factory API key. Cloud workers and shells are excluded. A separate incremental JSONL projection keeps up to 24,000 recent characters of visible user and assistant text, independently of the tool-heavy Thread window. Tools, tool results, thinking, hooks, hidden records, system-reminder blocks and attachments are not input; only the previous generated subject accompanies the recent text. One scheduler covers all floors with at most two calls at once, coalesces pending changes, skips unchanged text (including across restarts), and checks for final text after a turn finishes. It rechecks worker identity before publishing and drops stale results after removal, `/clear`, session/cwd changes, settings changes or shutdown. Calls use the Droid SDK with a fresh temporary HOME and neutral working directory, hooks and cloud sync disabled, no personal/project configuration or login files, and only the selected custom model definition when needed. Every listed tool is disabled; because Droid currently retains ToolSearch, an unexpected tool attempt rejects the result rather than publishing a label. The exact selected model and effort must resolve; there is no model or personal-profile fallback. A local prompt preview appears immediately, including while generation is disabled or the Office has no Factory key, until a generated label replaces it. Previews never become model input or overwrite generated labels. Failures keep the last successful label, retry with backoff and appear in Settings. Office-wide preferences live in `.factory-flow/worker-labels.json`; generated labels, their `updatedAt` timestamp and their text digest live with each floor's saved workers, and `office_roster` and `team_status` surface `taskLabel` (`generated` vs `lead`/`prompt` source, `updatedAt`, and `stale: true` when Worker labels are off) without adding label metadata to Grok Bot webhook payloads. Live permission questions, missing worktrees and errors take priority over summaries, without changing worker names or Droid session titles.

- **Windows after a Mac app update.** The app saves whether its companion window was open before installation, then consumes that flag once after restart. Older office/companion flags map to the one ordinary window. Closed windows leave the app in the menu bar.

- **Remote host app updates.** Android's **Me → About → Host desktop app** reads `GET /api/host/update` and explicitly sends `POST` with `check` or `install` and the offered version. The normal device/LAN gate applies; writes also require the office's origin or a paired device's bearer header. A private Node IPC channel connects only the office child started by the Mac app to Electron's `Updates` controller. The route accepts no URL, file path or shell command. Local and remote clients share one check/download, phase, progress and error state; stale or duplicate install requests are refused. Remote checks and installs do not require opening or confirming a window on the Mac. Nothing downloads until installation is confirmed. The existing electron-updater feed and Squirrel.Mac signature verification still decide what may install, and only then does the app stop the office with workers kept and restart into the update. Closing the remote view stops its polling, not the host update, and commands are never queued or replayed after a disconnect. Standalone/source servers explain that the packaged Mac app must host the office; older servers return the clients' update-on-the-Mac fallback.

- **Companion floor navigation.** The web and native Mac companions show every available floor as a numbered chip in a horizontally scrolling row, in the same saved order as Android. The current floor is highlighted and brought into view on arrival; trackpad, touch and mouse-wheel scrolling reveal the rest. Left/Right and Home/End move focus between chips, and Enter or Space switches floors. In the native Mac companion, ⌘+ (also ⌘=) selects the next floor and ⌘− the previous, wrapping in saved order. These shortcuts work from terminals and composers, ignore held-key repeats, and leave open dialogs alone. External browsers retain their zoom shortcuts. Repository details stay in each chip's tooltip. Floor switching is disabled while disconnected or syncing, and **Add floor** (sharing the Add floor picker's `floor.repos`, `floor.folders`, `floor.add` and `floor.projectsDir` picker, with immediate `floors` broadcast before `floor.added`) and **Reorder floors** stay beside the row.

- **Companion empty panes.** Click an empty pane or its **Hire Droid here** button to open the hiring dialog, even when everyone on the floor is already open. The confirmed hire opens in that pane, regardless of later focus changes or automatic placement before confirmation. If the pane was filled or hidden meanwhile, it uses the normal available-pane selection instead. Existing worker picks and drag-and-drop still open those workers without hiring.

- **Team activity in companion threads.** A lead's Thread view includes a collapsed **Team activity** section for its local Droid children, identified by `WorkerInfo.lead`, not team badge names. - **Android app updates.** The app's `UpdateController` checks the public GitHub latest-release API on foreground entry, at most hourly per running process (15 minutes after failures), or immediately on a manual check. Its final version number is the commit count when that APK was built. `update/GitHubUpdates.kt` uses a separate unauthenticated HTTPS client with HTTP cache validators; downloads start only on **Update now**, stream to private cache and are checked against GitHub's SHA-256 digest and the installed package/signing key before a narrow, read-only `FileProvider` URI opens Android's installer. Failed checks don't block the office, finished APKs are reverified and reused, and the latest-release webpage is always offered as the fallback when a newer version is known. See [android/docs/updates.md](../../android/docs/updates.md).
- **Status.** `WorkerManager` in `src/server/workers.ts` is the façade the server and Office MCP use; it delegates to `src/server/worker-runtime/`: hook intake and status transitions (`hooks.ts`), the hook listener and spool replay (`hook-transport.ts`), outbox and notice delivery (`delivery.ts`), the per-launch settings overlay and system prompt (`launch-settings.ts`), process and PTY helpers (`process.ts`), activity and permission asks (`activity.ts`), in-memory worker state (`state.ts`) and `workers.json` persistence (`persistence.ts`). Droid workers start with a `--settings .factory-flow/droid-hooks.json` overlay, written again at every launch and resume: hooks (`SessionStart`, `UserPromptSubmit`, `PreToolUse`, `PostToolUse`, `Notification`, `Stop`, `SubagentStop`, `PreCompact`) post to `/hooks/droid?…&v=2`, a server bound to `127.0.0.1` and authenticated by a random per-worker token. The hooks use `curl` (0.5 second connect timeout, 2 seconds in all) when it's there and a small Node helper (`.factory-flow/hook.cjs`, run on the office's own Node through `runAsNode`) when it isn't; they merge for that process only and never edit your Factory settings. A hook never waits on an office that is down or restarting: when it can't deliver (the office refused it or couldn't be reached, but not when it took the hook and answered too late, which would replay it twice), it appends the event, with the worker's token and when it fired, to `.factory-flow/hook-spool/<worker>.jsonl` (mode 0600, at most 512 KiB, the oldest lines dropped first), and the office replays each worker's spool in order once it has taken its terminals back, and again 5 seconds later, skipping lines from an earlier run of its droid (another token) and anything older than a hook it already took. Spools of workers who left are removed at start. Whatever the office answers, the hook prints, so its reply reaches droid; `v` says the command does that. Droid reads its hooks once, so a worker the terminal host kept across an office update still runs the command it started with (no `v`, or the Node helper without `reply`, whose output that command throws away): the office takes its hooks as before and never answers them. Right after the overlay comes `--append-system-prompt-file .factory-flow/system-<worker id>.md`: the `worker.system` prompt filled in with the worker's name, written again at every launch and resume and removed when the worker goes home. When that prompt is empty, the flag and the file are left out. A worker's first message (its task, a subagent's brief, the carry-on after a restart) is not passed on droid's command line, because droid started with a prompt argument never opens `/rewind-conversation` in that run: the office pastes it into the input box when `SessionStart` says droid can take input, or, when no `SessionStart` has come 15 seconds after the start, once the screen shows the `? for help` footer. Until then it is saved in `workers.json` with the terminal, so an office restarted before `SessionStart` (its terminal kept in the host) still types it in, once. Every hook carries `transcript_path`, which the office keeps (when its file is named after the session) and reads first for the worker's model, its Thread and its worker labels, before looking for the session file itself; only a session that has sent no hook yet (a worker restored by a restarted office, before its first hook) is looked for in `~/.factory/sessions`. A `PostToolUse` of `TodoWrite` from the worker's own session (not a subagent's) sets `WorkerInfo.todos` from its structured `tool_input.todos` (`src/shared/todos.ts`): how many items are done, of how many, and the one in progress. The card over its head in the office, its row in the web companion's sidebar and its card on Android show it as a bar with *3/5* and the item in progress (the companion's as a tooltip). It is saved in `workers.json`, cleared with its conversation (a `SessionStart` with `clear` or a new session), when a list comes with no items, and once every item is done and the worker comes to rest. A `Notification` with `permission_prompt` or `elicitation_dialog` means *needs input*, and one with `idle_prompt` means *done*. A `PreToolUse` of `AskUser` (or `AskUserQuestion`, `request_user_input`) also means *needs input*, and `WorkerInfo.ask` carries what is asked: the whole questionnaire (questions, topics, options and whether each takes several answers), or for a permission prompt the tool call it is about (the tool, its command or file, risk and summary). The web and Android answer cards show that text instead of what fits on the terminal's screen; the answer is still typed into the terminal, and the office never answers a permission with a hook decision. `workers.json` keeps `ask` with a waiting terminal's saved status, so a terminal the PTY host kept through a restart is picked back up still asking the same thing. The prompt is answered when the next tool starts or when the tool it asked about finishes (`PostToolUse`). `Stop` comes before droid stops, and a Stop hook (the office's own, below, or one you set up) can make it continue, so a Stop is *done* only once 1.2 seconds pass with no other hook, and then not while the screen shows a dialog or a spinner that is still printing. A Stop that comes while the worker *needs input* (a question cancelled with Esc) is *done* the same way. A message queued with Ctrl+Enter during a turn runs after that turn's Stop with no `UserPromptSubmit` of its own: the office counts the Ctrl+Enters it types and lets a Stop pass for each, so the worker stays *working*. Clear queue (Ctrl+X), or a Stop whose screen shows the input box with nothing queued, sets the count back to zero. A Stop within 3 seconds of Esc or Ctrl+C is a cancel, never blocked. `PreCompact` shows *Compacting its conversation* until the `SessionStart` with source `compact`, which keeps the same conversation and turn. A worker whose Stop has come is not mid-turn, so a restart in that window never sends it the carry-on prompt. A subagent droid starts with the Task tool (only when Settings allow Task, see Subagents) posts with the worker's token under its own session, announced by a `SessionStart` with `calling_session_id`: its permission prompts and questions count for the worker, while its own start, prompt and `Stop` don't, its `SubagentStop` ends a question it was asking, and the worker keeps (and resumes) its own session. Office notices go through the hooks too: a visit, a message from a lead, or a Whiteboard ping for a worker in the middle of a turn waits in its outbox (saved with its terminal in `workers.json`, so a restart that keeps the terminal keeps it) and comes back as `additionalContext` on its next `PostToolUse`, or as the reason a `Stop` is blocked, once (never a Stop that `stop_hook_active` says a block already continued). A worker at rest or asking, or one on an old hook command, has them typed in as before; notices still waiting when it comes to rest are typed in once nobody has typed into its terminal for 5 seconds. What goes through a hook always starts with `Factory Flow` (one whose rewritten prompt doesn't is marked `Factory Flow notice:`), which is how the Thread knows it and shows it as an *Office notice*. Hooks are what status follows; every second the office (`reconcile` in `src/server/workers.ts`, the patterns in `src/server/droid-screen.ts`) still reads the bottom rows of each agent's terminal as a safety net for what no hook said, and logs each correction it makes: droid's spinner line (`Press ESC to stop`), a permission prompt or AskUser dialog, or the `? for help` footer at rest. It locates the input box's borders so multiline queued input cannot push the spinner out of view, reads up to 8 rows above the box for the spinner (past queued messages or a todo list), and text inside that box is not a status signal. A dialog counts only when its key hints (`inspect approval details`, `ESC stop agent`) are below any `? for help` footer, since a dialog takes the footer's place: a reply or the input box quoting them above the footer is at rest. Once the screen has said one thing for 4 seconds with no hook in that time, a status it contradicts follows it: a busy screen that is still printing means *working*, a dialog means *needs input*, and an idle screen with nothing printed for 4 seconds means *done*. A quiet screen that still shows the spinner is never completion.
- **Shells.** The web companion's **Shell** button and Android's `hire.shell` send `worker.spawn` with `kind: 'shell'` and `deskId: 'auto'` (no prompt, no worktree), which opens a plain login shell in the floor's checkout in the next free slot for dev servers, git or tests, and then opens the new shell's terminal. A shell streams like any worker's terminal, has no hooks and no model, and is not counted by the subagent limits. Android handles hire results above the tabs, so Shell opens from Asks as well as Office; a Droid's pending Open snackbar never delays it. Wide Office views keep the shell beside the worker list.
- **Isolated branches.** When you hire with a task, you can tick *own git worktree*. The worker then gets its own `flow/<name>` branch under `.factory-flow/worktrees/`, so parallel workers never share a checkout. Factory Flow only lists, protects and prunes `flow/*`; the `office/*` branches Droid Office makes in the same repository are never its to touch. Just before cutting it (a hire or a subagent), the office runs `git fetch --no-tags origin <branch>` (`src/server/worktrees.ts`, 15s, a burst of hires shares one fetch per branch, and a failure is logged once). `<branch>` is the selected floor branch when set, otherwise the default branch (`Worktrees.defaultBranch`: what `refs/remotes/origin/HEAD` points at, else `main` or `master` on origin or here) while *Where fresh workers start* is *Latest floor branch* (`src/server/saved-switch.ts`, the office's `.factory-flow/fresh-main.json`, on by default), else the branch the checkout is on (and the checkout's branch when there is no default branch). It branches from `origin/<branch>` when the local `<branch>` is strictly behind it or missing, so pull requests merged since you last pulled are in it. It branches from the local branch instead when that already has all of origin (commits not pushed yet), or when there's no origin or the fetch fails. When both have moved on, it starts from origin and a toast says how many local commits it left out (`starts from origin/main, without the N commits on main that origin doesn't have`). The floor's own checkout is never moved or cloned; the fetch only refreshes the base a worktree is cut from. The office keeps `worktree.branch` on the branch the worktree is actually on: it reads it when the worker comes to rest or its process exits, when the office starts, when the pull-request list arrives, and before **O** or sending the worker home. A branch the worker creates itself (`git checkout -b`), or a rename of the office branch (`git branch -m`, matched only by the reflog line `Branch: renamed refs/heads/…`), is the one that is followed, and `worktree.made` remembers `flow/<name>` until that rename. Deleting the office branch is not a rename, so send-home then removes only the worktree and leaves the branch the worker is on. Sending it home deletes the branch the worker made. The office branch is deleted only when it holds nothing that branch lacks, and is kept while it still has commits no remote, the project's checkout, or the current branch has — those commits still count as work after the worker has switched away. A branch that already existed when the worker was hired (its reflog is older, like `main`) is never deleted. `Worktrees.sendHome` makes that choice and does the deleting, for one worktree and for each worktree of a worker across repositories, and says what it deleted and kept and why. Gun dismissal (`Worktrees.dismiss`) does not use it, and `factory-flow prune` keeps its own `describeWork` and `--force` check before deleting; it protects only workers recorded by the office and uncommitted or unpushed work, and outside-started processes are not checked. When you send that worker home you choose whether to keep the worktree and branch, delete the worktree, or delete both, and the office warns you first about uncommitted changes or commits no remote has. Those commits include what the worktree's own `HEAD` holds while it is detached (`git checkout --detach`, a rebase), which no branch may have, so sending it home with no choice keeps the worktree. `factory-flow prune` clears out whatever was kept, once it is safe, and treats `worktree.made` as that worker's branch too. With *Workers whose pull request merged* set to go home by themselves (`src/server/leave-on-merge.ts`, saved in `.factory-flow/leave-on-merge.json`), each floor looks again whenever the PR list comes back or a worker changes, and uses the same call as the purple bubble (`workerPr` in `src/shared/status.ts`). A worker goes with the office's usual check for work its worktree would lose, except that commits up to the merged PR's head (GitHub's `headRefOid`, GitLab's `diffHeadSha`) count as delivered, even once the forge has deleted the branch.
- **Fresh workers and the checkout.** With *Latest floor branch* on, a fresh agent hired without a worktree at a desk (by you or the boards; not a subagent or shell) waits for `git fetch origin <floor branch (the repository default when not overridden)>` like a worktree hire, and `WorkerManager.spawn` calls `Worktrees.freshen` before its terminal starts. That does nothing when the checkout is on the default branch and has all of `origin/<floor>`. Otherwise it leaves the checkout alone and toasts why when someone else is in it (another office worker without a worktree whose terminal is running, a worker mid-turn blocks any move, while a worker at rest only blocks leaving the branch it is on, so a checkout on a stale `main` is still fast-forwarded), when a merge, rebase, cherry-pick, revert or bisect is under way, when HEAD is detached, or when tracked files have uncommitted changes on another branch. From another branch it then runs one `git switch`: `-C <floor> origin/<floor>` when the local branch is behind origin's (or `--create … --track` when there's no local one), so a refusal leaves everything as it was, else plain `git switch <floor>`. On the default branch and behind, it runs `git merge --ff-only origin/<floor>`. Every switch and merge passes `--no-overwrite-ignore`, so an ignored local file is protected too if the destination starts tracking it. A default branch with commits origin lacks is switched to but not moved, with a toast. The floor's `project.branch`, which the Changes window of a worker in the checkout diffs against, follows the switch. Nothing stashes, resets or deletes. The same `freshen` runs without a hire, from `WorkerManager.settleCheckout`, whenever a floor's pull request list arrives and *Latest floor branch* is on: when the checkout's branch has a merged PR whose `headRefOid` is the commit the checkout is on (`Worktrees.delivered`, so a squash merge counts and a branch with newer commits doesn't), it fetches and switches back to the floor branch even with workers at rest in it, since nothing on that branch is left to come back to. It stays silent when it has to leave the checkout alone and tries again with the next list, and toasts only when it switched. A subagent's worktree starts from `Worktrees.resolve` of `--from` (a local branch, `origin/<x>`, a branch only on origin, or any commit) or of its lead's `HEAD`, read in the lead's worktree; with no `--from` that commit is moved up to origin's copy of the lead's branch when it is strictly behind it (`Worktrees.caughtUp`), after that branch is refreshed. An explicit origin branch is fetched independently of *Where fresh workers start*, with a refspec that updates its remote-tracking branch even in a single-branch clone; a local branch, tag or commit needs no fetch. `worktree.from` is the branch the Changes window diffs against; it is also the PR target when it exists on origin, otherwise the checkout's pushed branch or the default branch is used.
- **Worktree setup.** `src/server/worktree-setup.ts` and `src/shared/worktree-setup.ts`. Once a worker's worktree is cut (a hire or a subagent), the office works out what it gets from the worktree itself, which is on the branch the work starts from: the floor's own setup from ⚙️ Settings (the floor's `.factory-flow/worktree-setup.json`) if it has one, even an empty one; else `worktree.setup` and `worktree.copy` in a committed `.factory-flow.json`, plus the patterns in `.worktreeinclude`; else the install the lockfiles at the root call for (one JavaScript package manager at most, then uv, Poetry, Pipenv, Bundler, Composer, Mix) and `/.env`, `/.env.*`. A `.factory-flow.json` that isn't valid counts as none, and Settings says why. When there's a command, or any untracked file matches, it writes a plan to `.factory-flow/setup/<worker>.json`, and the worker's first terminal runs a login shell with `node .factory-flow/worktree-setup.cjs <plan>; exec <agent>` (`&` on cmd.exe), so the agent takes the shell's place and a resume never sets up again. The script (the office's own node, `SETUP_SCRIPT`) deletes the plan, lists the checkout's untracked files with `git ls-files --others --ignored --directory --exclude=<pattern>`, copies each one that isn't in the worktree yet (a clone where the file system can, nothing under `.factory-flow/`), then runs the command with the shell in the worktree, with `FACTORY_FLOW_ROOT_PATH` and `FACTORY_FLOW_WORKTREE_PATH` set. A worker across repositories gets a step per repository, each with its own floor's setup. It posts `WorktreeSetup` to the worker's hook URL when it starts and when it's done: the desk card says *Setting up its worktree*, the 12-second check for a Droid stuck on a login waits until 12 seconds after the setup ends, and a failed command (it always exits 0) toasts and is put ahead of the worker's first message with the last 40 lines it printed. The command's output is piped through the script rather than inherited for that, because Droid clears the terminal when it starts. `worktreeSetup.get` and `worktreeSetup.set` read and change the floor you're on; `worktreeSetup` answers, and goes to everyone on the floor after a change.
- **Pull requests.** The Changes window's pull-request action for a worktree worker runs `git push -u origin <branch>` in its worktree, then `gh pr create` (or the floor's forge) with the task as the body and the commits listed. `<branch>` is the one the worktree is on now, which may be one the worker made itself rather than `flow/<name>`. The base is the branch the worktree was cut from (`worktree.from`: the default branch, the checkout's branch, or for a subagent its lead's branch), if that branch is on the remote, else the branch the checkout is on when it has been pushed, otherwise the forge's default branch. The Changes window uses the same pushed-branch check (`Worktrees.pushedBranch`), with the default branch as its last candidate, so a subagent's unpublished lead is not used as a PR target. Its diff still shows only what it changed relative to its lead. The PR number is saved with the worker, so the board can point back at the worker.
- **Across repositories.** A worker hired with other floors' projects (`WorkerInfo.repos`, `makeWorkspace` in `src/server/workers.ts`) gets a workspace folder, `.factory-flow/worktrees/<name>/` on its own floor, with a worktree of its own project and of each other one in it, all on `flow/<name>`, named after their checkouts. Each is cut from that checkout's fetched base (the same `git fetch origin <branch>` as a single worktree; the floor's checkout is never cloned or moved), and its `from` branch is what that project's pull request targets. Two checkouts of the same repository are refused, and so are more than 8 other projects. The workspace isn't a repository; the agent starts there with `GIT_CEILING_DIRECTORIES` set to its parent, so git run in it finds nothing instead of the floor's own checkout, and the `worker.repos` prompt is written there as `AGENTS.md`. If one project can't have its worktree, the ones already made are removed again. **O** pushes and opens a pull request in each worktree that has commits and no pull request yet (the issue's `Closes #n` only in the home project's; the others say `Part of owner/repo#n`), then puts a list of all of them between `<!-- agent-office:related -->` markers in each description, replacing the list on later presses. Sending it home runs `Worktrees.sendHome` in each repository, so a deleted office branch, a branch from before the hire and commits only on the office branch are handled there as in one project, and the note names each repository's outcome when they differ. A worker across repositories goes home by itself once no pull request of its is open on any floor's board, one has merged, and none of its worktrees holds work those merges didn't deliver; a failed check keeps the worker. `factory-flow prune` leaves a workspace alone while worktrees are in it, and in the other projects lists the worker's branch as checked out elsewhere (and prunes it once that office no longer lists the worker).
- **Changes.** While a worker's Changes window is open, the office runs `git status` and `git diff` in that worker's checkout as soon as its `PostToolUse` hook says a file edit or a command finished (`toolRefresh` in `src/server/hook-refresh.ts`), and every 10 seconds otherwise for edits no hook reports (every 2 seconds for a shell, which has no hooks), and pushes the file list when it differs. A look asked for while one is under way runs once more after it. A worker across repositories has a tab per repository, each diffed against that floor's own branch. The diff is against the merge base with the newer of the branch the office was opened on and its origin copy, so it covers the worker's commits and its uncommitted edits, and a pull request merged on the forge that the project never pulled is not shown as the worker's change. Uncommitted edits stay listed even when they undo a change already committed on the branch; their diff and picture preview compare against `HEAD` (or the index) then. Within the list's limit, files with uncommitted edits come first. Commit is `git add -A && git commit`, discard is `git restore` / `git clean` (or `reset --hard` for everything), and Open PR checks the checkout's whole `git status` again and refuses while anything is uncommitted, then pushes the branch and runs `gh pr create`. Open PR and the Changes window's pull-request action share `src/server/open-pull.ts`: the same dirty check, open-pull lookup and push, and one base choice, the first of the branch the work was cut from, the branch the office opened the floor on, the checkout's current branch and the default branch that exists on origin. Commit & open PR runs nothing itself: it is a `worker.prompt` with the `changes.ship` prompt filled in from the task card (`WorkerInfo.task`), the tab's branch, its pull-request base and, across repositories, the tab's folder in the workspace; a working agent gets it queued behind what it is doing. Only an agent gets the button, and only on a branch of its own with something to commit or push. **T** attaches the window to the worker's terminal like the terminal window does (`worker.attach`, detached when Changes closes), but never types to it or resizes it: it takes the PTY's size.
- **Terminals.** Each worker's PTY lives in `factory-flow-ptys` (`src/server/ptyhost.ts`), a detached process the server starts for each floor and talks to over a Unix socket in that project's `.factory-flow/`. Outbound WebSocket delivery to windows and companions, its backpressure and the coalescing of off-floor screen updates live in `src/server/server-runtime/transport.ts`. On SIGTERM the server leaves the PTYs running there, and the next server takes them back with a snapshot of each screen. Hooks that fire in between are spooled and replayed once it's up (see Status). If no server comes back within 30 minutes, the PTYs are ended. The server mirrors each PTY in a headless xterm. The PTY owner (`ptyhost.ts`, or the in-process fallback when unhosted) answers terminal capability queries in stream order — Kitty keyboard (`CSI ? u`), Kitty graphics (`APC G` with `a=q`, advertising direct base64 `t=d` and `U=1` Unicode placeholders while rejecting local-file `t=f`/`t=s` transfers so CLIs stream inline), cell/window pixel geometry (`CSI 14/16/18 t`, reporting 18×36 device-pixel cells, a 9×18 cell at Retina density, because CLIs such as Droid downsample inline images to the reported cells before sending them; `KITTY_CELL_PX_W`/`H` in `src/shared/kitty.ts`), `OSC 10/11` theme colors, `XTVERSION` and xterm's device/cursor reports — while browser and Android mirrors suppress duplicate replies. Snapshots (`src/server/screen.ts`) replay active Kitty images, animation frames, direct placements, mouse encodings and Kitty keyboard stacks across restarts and late-joining windows. Open terminals in the Changes log, `/dashboard` web companion (`src/client/term-kitty.ts`) and Android WebView (`assets/terminal/kitty.js`) render `U=1` virtual placements, direct placements, zlib-compressed payloads and animated frames on a high-DPI canvas layer while hiding `U+10EEEE` placeholder glyphs in xterm and encoding negotiated `CSI u` keystrokes (`src/shared/kitty.ts`, `core/KittyProtocol.kt`). Interactive terminals in `/dashboard` expand Kitty images into the shared fullscreen viewer (`src/client/ui/picture-viewer.ts`) via a hover expand button, `Cmd`/`Ctrl`+click, or a plain click in a normal shell (`normal` buffer with `mouseTrackingMode === 'none'`); Android Raw TTY opens a tapped Kitty image in its shared pinch-zoom viewer (`ThreadPictures.kt`), showing the first frame for animated images and ignoring evicted ones. Each window that opens the terminal gets a serialized snapshot, then the live stream; closing one window detaches only it. Compact screen frames (`src/server/screen-frame.ts`) carry per-row diffs a few times a second, with `U+10EEEE` stripped from text runs (and from `plainTail`, terminal search and Android TalkBack text) and coalesced image placements plus one-time image payloads. A terminal wider than the preview also sends the scrollback rows just above it (`screenHistoryRows` in `src/shared/protocol.ts`, `src/server/screen-frame.ts`) so the preview keeps its text at a normal shape. A cleared screen and a program on the alternate screen show only the screen. The PTY takes the size of whichever window typed into it last or whose companion pane changed size. Android draws the snapshot and stream in xterm.js inside a WebView, so it keeps the snapshot's scrollback. Its **Phone** view, the one a worker's terminal opens in (a cloud worker's opens in Desktop), sends `term.resize` when selected or when its viewport changes, measured at readable text size; switching it off or leaving the terminal sends back the size from before, unless another window resized it since, in which case the phone switches to Desktop. Its **Desktop** view never sends `term.resize`. The server also remembers, per phone connection, the size each terminal had before that phone's first resize, and when the connection closes it puts back every terminal still at the size the phone last set. A paired desktop browser is not a phone: it gets no `PhoneSizes` record, so closing `/dashboard` never restores a phone size. A browser that attaches while another window already has the terminal adopts that size until it types or its companion pane changes size. Layout switches, maximizing and splitter changes fit every affected terminal without requiring focus. Initial observations stay passive; hidden boxes do not resize the PTY, and stale worker metadata or earlier resize acknowledgements do not undo a newer local fit. Compact screen broadcasts serialize only for ready receivers; a backpressure drop requests a full recovery frame on the next eight-second keyframe boundary rather than sending unchanged periodic keyframes. The browser deduplicates identical rows, placements, scrollback and cursor state, and screen-change events wake visible previews both for text updates and for Kitty images that finish decoding asynchronously.
- **Scrollback and search.** Every 15 seconds, for each worker that printed something new, and again as the office shuts down, its last 3,000 lines are serialized, colors included, to `.factory-flow/scrollback/<worker>.ansi`. A worker that starts again (after a restart, or when you resume it) gets its old lines replayed into its terminal first, then a dim *office restarted* line. `GET /api/search?q=` matches case-insensitively, treating runs of whitespace as one space, over each worker's terminal buffer. It returns the newest lines first, each distinct line once. The browser finds the hit again in its own copy of the terminal and scrolls to it. An office from before this release may still have a `chat.jsonl` in its `.factory-flow/`; it is left on disk and never read.
- **Pictures in prompts.** `src/client/ui/images.ts` uploads each pasted or dropped picture as it's added (`POST /api/prompt/image`, which checks the file's first bytes, not the browser's word for it, and keeps it in `drops/staged/<id>/`; `DELETE` takes it out). A message that carries a prompt (`worker.spawn`, `worker.prompt`) lists the picture ids in `images`, and the server turns them into paths: `DropStore.adopt` copies each into the worker's own drops and `withImages` (`src/shared/drops.ts`) appends the numbered list to the prompt. The ids stay staged until the message has been handled. Closing a dialog without sending deletes its staged pictures.

- **Subagents.** A subagent is an ordinary worker whose `WorkerInfo.lead` names the worker that hired it; `workers.json` keeps it across restarts, and a lead that doesn't come back (or is a subagent itself) leads nobody. Apart from that, `WorkerInfo.team` is what a worker's team badge shows (`src/shared/team.ts`): the team's id (the id of the worker that formed it), the role (`lead` or `member`), its accent and emblem, and the lead's name. A lead's first hire gives it a `lead` badge with the first accent and emblem that no team still on the floor wears (`pickTeamLook`; else a pair nobody wears, so two teams never differ by color alone), and every subagent it hires gets the same badge as `member`. The badge is display only: when the lead leaves, its subagents lose `lead` (no reports, no supervisor) but keep `team`, so they still show whose team they were on; a subagent whose lead left that hires for itself takes a new `lead` badge under its own id. Nothing reads `team` for reporting, hiring or permissions. `workers.json` keeps `team`, and on restore `settleTeams` checks each badge against who leads whom now: a lead badge under another worker's id, or a member badge naming a lead that is on the floor but isn't its lead, is dropped, a lead with subagents but no badge (an office from before markings) gets one, and each subagent wears its lead's. A subagent whose lead was already gone in an office from before markings wears nothing; no history is made up. The companion shows the badge as the team grouping in the sidebar (see Companion worker teams). A `data-wb-ping` button's first press records `state.pinged[name]` along with the action; the window and the Android app tell the frame who the buttons reach (`buttonTarget` in `src/shared/whiteboard-ping.ts`: the content stamp's author, while it's an agent on the floor) and the SDK disables them otherwise. After the batch commits, `src/server/whiteboard-buttons.ts` types the `whiteboard.button` notice into that worker as `buttonDelivery` says (steered through its hooks, typed, resumed, or held in its outbox while it's starting or asking), and a press it can't deliver has its `pinged` entry deleted so the button works again. The renderer (`src/server/whiteboard-render.ts`) is a headless Chromium driven by `playwright-core` with Chromium's own sandbox on (`src/server/whiteboard-browser.ts`). Each render is a fresh browser context with every permission denied, loading the card the way the window does from a pinned snapshot that keeps its blobs on disk while it runs (capping open-ended media `Range` fetches at 2 MiB per chunk so large videos stay bounded over CDP), at 1280 pixels wide. It waits for fonts, network quiet and the page to stop changing (10 seconds at most), draws the stickies, pictures and comment pins, and captures the full page as 1280×2048 tiles (8 at most) plus a 640×400 thumbnail. Renders are debounced per card and run two at a time; a newer image is never replaced by a slower older one, and a failed render keeps the last good image. The local network is granted to the renderer's own page only so cards can reach machines on it, and the office's own addresses stay blocked. Images are kept in memory, so the office renders every card again when it starts. `whiteboard_read` with `png: true` renders the read's own snapshot as MCP image content, or says why it couldn't; without a browser, the board says renders are unavailable and why, and everything else works. Taking a floor off stops its watchers and renders and deletes nothing.
- **Viewport input.** The artifact SDK forwards trackpad wheel/pinch, middle-button drags, temporary Space-pan and navigation shortcuts (including **F** for full screen) over the same frame-and-nonce-bound bridge. Space on a focused button, link, video or audio stays with it, and while something in the page is full screen itself (and for half a second after it gives the screen back) no shortcut, Space or Esc is forwarded. Pointer coordinates are mapped from the frame into the viewport; device deltas stay in screen pixels. The surface accumulates navigation once per animation frame, retains fractional positions, and numbers scroll requests so delayed layout messages cannot rewind a gesture. Nested scroll regions and form input remain native, and rendering never forwards navigation.
- **Files.** The Factory window's **Files** tab. `src/server/docs.ts` lists a floor's Markdown (`.md` and `.markdown`, `GET /api/docs`) or all non-binary text files (`GET /api/docs?all=1`) with `git ls-files --cached --others --exclude-standard`. That covers what's committed plus new files that aren't ignored, so `node_modules`, build output and `.factory-flow/` stay out of the list. A folder that isn't a git checkout is walked instead, skipping hidden, dependency and build folders. Each doc's title is its front matter `title:` or its first heading, read from its first 4 KB, and the list is cached for a few seconds. Editable text files can be read (`GET /api/docs/file`, up to 2 MB, with NUL-byte binary sniffing and `mtime`), searched across content (`GET /api/docs/search`), and saved atomically through a sibling temporary file and rename (`PUT /api/docs/file`, owner-only, returning `409` when `baseMtime` no longer matches the file on disk), and pictures can be fetched for a doc (`GET /api/docs/picture`, up to 10 MB), all inside the checkout after following links. Each listed file carries its uncommitted change from `git status --porcelain=v1 -z -uall`, by path from the project folder (`parseGitStatus`), and saving reloads the list so the tree's git colors follow. The tab (`src/client/ui/bookshelf.ts`) and `src/client/ui/editor.ts` provide **Preview**, **Edit** and side-by-side **Split** modes backed by CodeMirror 6 with lazy language grammars from `@codemirror/language-data`, the project tree (`src/client/ui/file-tree.ts`: virtualized rows, keyboard navigation, the context menu and go-to-file ranking, on `buildDocTree` and `docTreeRows` in `src/shared/docs.ts`) with file-type icons from `src/client/ui/file-icons.ts`, dirty-state guards and conflict reload/overwrite. The browser renders Markdown with the same sanitizer as issue and PR text. Links to files that aren't docs point at `…/blob/HEAD/` on GitHub or `…/-/blob/HEAD/` on GitLab, from the floor's `origin` remote.
- **AutoWiki.** `src/server/factory/wiki.ts` ([docs/factory.md](../factory.md#autowiki)) keeps each floor's AutoWiki in the `wiki` slice: the newest run of the floor's repository (from `GET /wiki`, matched to its `origin` remote) and its history (`GET /wiki/history/{repoUrl}`, the full https URL, encoded). Page trees, pages, searches and the .zip export are read through `/api/factory/wiki/…` when the tab asks, and cached, since a run never changes once uploaded. **Generate** (`wiki-run.ts`) fetches `origin`, checks its default branch out as a detached worktree at the floor's `.factory-flow/wiki-run/`, and runs `droid exec --auto high -m <model> "/wiki <rule>"` there with the office's Droid command and the office's Factory key as `FACTORY_API_KEY` in that one process's environment; `/wiki` uploads the wiki as its last step, to Factory only. A runtime `--settings` file beside the worktree (`.factory-flow/wiki-run-settings.json`) sets every subagent complexity tier to the same model, so the owner's own subagent models don't apply to it. Once a run uploads, `.factory-flow/wiki-run-models.json` remembers which model wrote it, since Factory's copy may not say. One run per floor. Its last lines (scrubbed of the key) go to browsers once a second, **Stop** ends its whole process tree, and the worktree is removed when it ends. A note in `.factory-flow/wiki-run.json` says one is running: an office that stops mid-run ends it, and the next one cleans up after it and shows the run as lost.
- **Floors.** `floors.json` in the office's `.factory-flow/` lists the floors: each one's checkout and colors. The home folder (`~`) is always a floor, named **Home**: the office adds it after your projects at every start if it isn't there, and it has no remove control in the floor list and can't be taken off. Its own `.factory-flow/` goes in `~`. Adding a floor records the path of a folder that already exists: nothing is cloned, copied or moved. A git checkout (a folder with a `.git` of its own) has to be in the workspace folder (the office searches it up to four folders deep for `.git`, skipping hidden folders and `node_modules`), and a checkout outside it is refused. Any other folder the office can read and write, anywhere on the machine, becomes a **plain floor**; the top of the disk and folders inside a `.factory-flow/` are refused. The Add floor window's **📁 Browse** lists a folder's subfolders through `floor.folders` (`Building.folders`: hidden ones left out, sorted, at most 500, each marked when it is a checkout), starting in the workspace folder. A floor is plain when its folder has no `.git` of its own, checked when the floor opens, so Home is plain unless `~` is a repository, and a folder inside someone else's checkout is plain too. A plain floor (`Floor.plain`, `FloorInfo.plain`) runs `NoBoard` (`src/server/forge.ts`) and `NoPipelines` (`src/server/pipelines.ts`) instead of GitHub, GitLab and their pipelines, so nothing asks `gh` or `glab` about it, and the room puts away the Issues, Pipelines, PR and CI boards with their ☰ menu entries and palette entries (`Office.setPlain`). Hire controls offer worktrees only on git floors outside Home. It has no worktrees, branches or Changes window, and it can't be one of a worker's other repositories. Its workers' system prompt leaves out the branch policy, and a subagent's brief says it works in the floor's folder. Its `Worktrees` and every worker's terminal run git with `GIT_CEILING_DIRECTORIES` set to the folder's parent, so git there says it isn't a repository rather than finding a checkout the folder is inside. A folder that becomes a checkout later (`git init`) is a git floor from the next start. A symlink to a checkout that already has a floor is that floor: the office compares the real directory and keeps the path already saved. An alias already in `floors.json` is not opened as a second floor. Taking that floor off removes its saved aliases too, so it stays off; its checkout, pictures and workers stay on disk. A symlink inside the workspace that points outside it is still refused. A floor whose origin is on GitLab gets GitLab boards: issues and merge requests come from GitLab's GraphQL API, and comments, merges, closes and assignments go through its REST API. Both forges share one list (`src/server/board-list.ts`): issues sort by priority, a label edit shows on the cards at once and stays until a list asked for after the edit comes back, the repository's labels are remembered for a minute, and a close the list still shows as open is looked at again 3 seconds later. Each floor runs its own workers, GitHub or GitLab boards, pipelines and changes watcher in its checkout. A floor you're not on, with nothing running, asks GitHub about its boards every 10 minutes instead of every 90 seconds. A worker's `git push` or pull request or issue command (`gh pr create`, `glab mr merge` and the like, `toolRefresh` in `src/server/hook-refresh.ts`) has its floor, and every floor it works across, read the boards again 1.5 seconds after the last of a burst and the pipelines 6 seconds after a push or merge, instead of waiting for the next poll; a branch switch updates its card at once. Each connection gets the live terminal stream of the floor it's on, plus building-wide worker and pull-request roster updates (`welcome.building`, `building.worker`, `building.remove`, `building.pulls`) and full screen snapshots for off-floor workers waiting on input (`needs_input`), so companions can list, answer, fork and dismiss workers across every floor without switching floors first.

- **Paired phones and desktop browsers.** `src/server/devices.ts` keeps paired devices in the office's `.factory-flow/devices.json` (id, name, SHA-256 of the device token, `pairedAt`, `lastSeenAt`, and `kind: "browser"` only for a desktop browser). Phone records keep their old shape. The file is written to a temporary file and renamed into place, mode 0600. Every HTTP request past the static files and the public `/dashboard` and `/open/*` shells, and every WebSocket upgrade, goes through one gate (`access` in `src/server/server-runtime/access.ts`, applied by the request router in `src/server/server-runtime/http.ts`): a device token (`Authorization: Bearer`, else `?d=`) is checked against every stored hash with `timingSafeEqual`, and decides on its own, so a forgotten one is a 401 even on loopback; without one, it's loopback or the LAN token, as before. On `/ws`, a device token in the `Authorization` header skips the `Origin` check, because a native client can't always put that header on a WebSocket; `?d=` does not skip it. A browser request that sends an `Origin` must be same-origin even with a device token. `POST /api/mobile/pair` passes only the LAN gate (a device token doesn't pair another device) and refuses a cross-origin `Origin`. A browser pair also requires that same-origin request and `{"kind":"browser"}`; the response adds `device` beside the existing `deviceId`, `token` and `office`. The Phone window's own routes, `GET /api/mobile/pairing` and `DELETE /api/mobile/devices/<id>`, answer only loopback with a same-origin request (a matching `Origin`, or `Sec-Fetch-Site: same-origin` on a GET) and no device token. Tailscale is read with `tailscale status --json` (2 seconds at most, cached 30 seconds, `src/server/tailscale.ts`); addresses in 100.64.0.0/10 count as Tailscale, never Wi-Fi, in the join URLs and the pairing code. A paired device's open connection marks it seen at each 20-second heartbeat. Forgetting it closes its sockets with 4401. The desktop companion is `/dashboard` on the same host and port: a generic page with no office data, then the saved browser token in origin-scoped `localStorage`. The Web companion window shows network names and **Copy pairing link** buttons rather than bare addresses; the copied URL includes this start’s LAN token. **Open here** opens the local companion without pairing. A remote browser opened without a key explains that it needs the complete pairing link and has not sent an approval request to the host. The key is removed from the address bar on arrival, so the browser must pair before refreshing. Pairing on a LAN address does not pair a MagicDNS name or another port. Whether the web companion is on is `web-companion.json` in the office's own `.factory-flow/` (`src/server/web-companion.ts`, on by default), switched by `PUT /api/mobile/companion` from the office's own page. Off, a browser pair is a 403 (`companionOff`), a browser device token and `hello?client=dashboard` are refused, `/ws` upgrades from the companion are refused and its open sockets are closed with 4403; phone tokens are not affected.
